## Intent

Build a Windows-local Codex companion panel that shows current conversation token usage and estimated generation speed, with a manually launched Pelican benchmark.

## Confirmed facts

- The user confirmed a Windows-local companion window.
- The workspace was initially empty and is not a Git repository. `PLAN.md` is the only current project file.
- Local Codex CLI is 0.162.1. The local sessions directory contains JSONL files; only file metadata and count were inspected.
- The Codex config reference documents built-in `tui.status_line` identifiers, not a public custom renderer command.
- Reference implementations: https://github.com/stormzhang/token-tracker and https://github.com/Moviw/codex-statusline.
- `Get-Command codex -All` found `codex.ps1`, `codex.cmd`, and native `codex.exe` candidates. `codex exec --help` confirmed stdin prompt input and `--json`; `codex debug models` lists `gpt-6-astra` and `gpt-6.1-sol`, each supporting `low|medium|high|xhigh|max|ultra`. Session filename metadata check found UUID-suffixed rollout files in the sessions directory; contents were not read.

## Scope

- A local browser companion served only on IPv4 loopback.
- Read local Codex session telemetry and show input/output/total token counters.
- Estimate output tokens per second from successive local usage snapshots only when counters and monotonic timestamps support it; otherwise show unavailable.
- Run a fixed Pelican benchmark only after an explicit user action. Keep answers, scores, and user-selected baseline local.
- Add focused parser, speed, scoring, server-security, and runner tests, plus Windows setup and privacy documentation.

## Non-goals

- Patching Codex, changing Codex configuration, hooks, or shell profiles.
- Background model calls, telemetry upload, or displaying conversation prompt/response text in the usage panel.
- Claiming one benchmark run proves model degradation.
- Publishing, deploying, committing, or pushing.

## Implementation plan and ownership

One execution agent owns all project writes to avoid overlapping file ownership in this empty workspace.

1. Bootstrap: `package.json`, `src/server.js`, `src/public/index.html`, `src/public/app.js`, `src/public/styles.css`. Use Node.js built-ins and native browser APIs with no runtime or development dependencies. `npm run dev` starts the server on the fixed address `127.0.0.1:4173`; on `EADDRINUSE` it exits with a clear message rather than selecting another port or binding another interface. Print the URL only after a successful bind. `npm test` runs `node --test`; `npm run build` runs `node --check` on exactly these shipped JavaScript files: `src/server.js`, `src/public/app.js`, `src/telemetry/session-reader.js`, `src/telemetry/usage.js`, `src/telemetry/speed.js`, `src/benchmark/cases.js`, `src/benchmark/runner.js`, `src/benchmark/store.js`, and `src/benchmark/scoring.js`. No `tsconfig.json` is used.
2. Telemetry: `src/telemetry/session-reader.js`, `usage.js`, `speed.js`. Parse bounded Codex JSONL tails defensively, tolerate unavailable data conservatively, deterministically select a session or report ambiguity, and never return transcript content.
3. Benchmark: `src/benchmark/cases.js`, `runner.js`, `store.js`, `scoring.js`. Run only on explicit UI action, use a fixed local CLI invocation, accept user scores, compare only compatible runs, persist locally, and state that one run is inconclusive.
4. Verification and docs: `tests/telemetry.test.js`, `tests/benchmark.test.js`, `tests/server.test.js`, `README.md`. Use the built-in `node:test` runner; cover parser edge cases, speed calculations, strict privacy filtering, server request validation, score aggregation, compatibility, and mocked subprocess outcomes. `npm run build` performs syntax checks and `npm test` runs the built-in tests.

## HTTP security protocol

- Bind only to `127.0.0.1:4173`; do not bind `0.0.0.0`, host LAN interfaces, or `::1`. If the port is occupied or IPv4 bind fails, fail startup rather than select another port or broaden binding. The fixed port also ensures only one server instance can own the benchmark store.
- Use fixed routes only: `GET /` serves packaged HTML; `GET /app.js` and `GET /styles.css` serve packaged assets; `GET /api/nonce` bootstraps the process nonce; `GET /api/telemetry` returns the schema below; `GET /api/benchmark` returns local benchmark state; `POST /api/benchmark/run` starts one fixed run; `POST /api/benchmark/score` saves scores; `POST /api/benchmark/baseline` selects an existing scored run; `POST /api/benchmark/cancel` cancels the active run. No route accepts a command, executable, path, arbitrary case, prompt, or cwd. Reject path traversal, alternate encodings of static paths, and query strings on state-changing routes.
- Methods outside the route table return 405 with `Allow`; unknown paths return 404. Require exactly one Host header equal to `127.0.0.1:4173`; reject userinfo, alternate host spellings, forwarded-host headers, and duplicate Host headers. When Origin is present, require exact `http://127.0.0.1:4173`. For `/` without Origin, require `Sec-Fetch-Site: none|same-origin` and `Sec-Fetch-Mode: navigate`. For `/app.js` and `/styles.css` without Origin, require `Sec-Fetch-Site: same-origin`, `Sec-Fetch-Mode: no-cors`, and the matching script/style destination. For `/api/nonce` without Origin, require `Sec-Fetch-Site: same-origin`, `Sec-Fetch-Mode: cors`, and empty `Sec-Fetch-Dest`. These routes reject missing required metadata. Read-only telemetry/benchmark GETs may omit Origin and Fetch Metadata, but reject any present cross-site metadata. Every POST requires exact Origin and `X-Codex-Companion-Nonce`; requests with `Sec-Fetch-Site: cross-site` are denied on every route.
- Generate one 256-bit nonce with the OS CSPRNG at process startup and keep it fixed until process exit. Successful `GET /` and `GET /api/nonce` responses that pass their Origin/Fetch Metadata rules return it in `X-Codex-Companion-Nonce`; every page load fetches `/api/nonce` with `cache: no-store` before enabling POST controls and keeps the value in that page's memory. A POST with a missing/incorrect nonce returns 403 with code `nonce_invalid`; only that code triggers one fresh nonce fetch and one retry of the same requestId and payload. Origin/Host failures use a different error code and are never retried. A fixed process-lifetime nonce lets reloaded pages and independent tabs bootstrap the same value without shared browser storage or rotation races. Compare nonce values in constant time. Never put it in URLs, HTML, logs, persistent browser storage, or benchmark data. Tests cover reload, independent tabs, simultaneous bootstrap, stale nonce retry, and no retry on Origin/Host failure.
- Require `application/json` and absent/identity `Content-Encoding` for POST; reject oversized bodies above 16 KiB while streaming, malformed JSON, and unknown request fields. Exact POST schemas (all reject unknown fields): `/api/benchmark/run` requires `{requestId, model, reasoningEffort}`; requestId matches `^[A-Za-z0-9_-]{16,64}$`, model is `gpt-6-astra|gpt-6.1-sol`, reasoningEffort is `low|medium|high|xhigh|max|ultra`; `/api/benchmark/score` requires `{runId, caseId, rubricVersion, scores}` where runId matches `^[0-9a-f]{8}-[0-9a-f]{4}-[1-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, caseId is one of `instruction-following|logic-grid|code-trace`, rubricVersion is `pelican-v1`, and scores has exactly `correctness, consistency, constraint_adherence`, each an integer 1-5; `/api/benchmark/baseline` requires `{runId}` with the same UUID format; `/api/benchmark/cancel` requires `{requestId}` with the same requestId pattern. A run requestId is durably associated with the canonical validated `{model, reasoningEffort, caseSetVersion}` payload and runId before a child starts. Reuse with that exact payload returns the same run state and never spawns another child, including after process restart; reuse with another payload returns 409. Repeated cancellation of an already cancelled request is idempotent; unknown requests return 404 and other terminal states return 409. Return 413 for excess size, 415 for wrong content type/encoding, 400 for malformed/schema-invalid bodies, 403 for Host/Origin/nonce failures, 404 for unknown IDs, and 409 for active-run conflicts, invalid state transitions, conflicting scores, or idempotency-key reuse with a different payload; benchmark storage/serialization failures return 503 and never start a child. JSON errors have shape `{ "error": { "code": string, "message": string } }`, with bounded non-sensitive messages.
- Add `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and a restrictive same-origin CSP to HTML and API responses. Never reflect request values into error text.

### Benchmark API allowlists and state changes

- The three case IDs, prompts, expected answer criteria, and scoring rubric are compiled into `src/benchmark/cases.js`; neither the UI nor POST payload chooses case IDs, prompts, paths, command arguments, cwd, or environment. A run always executes the complete fixed case set in its declared order. `model` and `reasoningEffort` are the only run configuration inputs and are restricted to the exact enums above. Before enabling runs, verify both model names and effort values against the installed CLI catalog; if the catalog cannot be read or lacks an exact supported value, benchmark routes report unavailable rather than accept an arbitrary value. Each requestId reservation and run record is atomically persisted before process launch so a process crash/restart cannot repeat an accepted model call; a reserved request whose outcome is unknown after restart is surfaced as `interrupted` and requires a new user action/requestId to run again.
- Serialize all run, score, baseline, and cancel mutations through one server-owned queue. Persist the requestId reservation atomically before spawning so simultaneous identical requests cannot start duplicate children; storage or queue failure returns 503 and starts no child. At most one run may be active. A new distinct run request while one is active returns 409. Scores may be submitted once per `(runId, caseId, rubricVersion)`; identical repeats are idempotent and differing repeats return 409. A score requires an existing completed run and one of its fixed case IDs; failed/incomplete runs return 409. Baseline selection accepts only an existing completed run with a score for every fixed case; selection is idempotent and persists the selected runId and its creation sequence. The anchor run determines the baseline model and exact compatibility key. For that model/key, the baseline cohort contains fully scored completed runs created at or before the anchor; the comparison cohort contains fully scored completed runs created after it. Other models and incompatible runs are excluded. For each run, compute the mean score per rubric dimension across its three cases, then compute each cohort mean giving each run equal weight. Display per-dimension differences and both sample counts; label the comparison `inconclusive` unless both cohorts contain at least five eligible runs. This describes observed scores for one model label and does not establish backend model-version identity or prove degradation. Cancel requires the active run's requestId; unknown IDs return 404, repeated cancel of an already-cancelled request is idempotent, and other terminal states return 409.

## Telemetry schema and privacy boundary

- Reader only consumes known event envelopes and only extracts: session id (36-character lowercase UUID), event timestamp (valid ISO-8601 string), event type from a fixed allowlist, and usage counters as non-negative safe integers. Recognize `session_meta` with `payload.id`, and `event_msg` with `payload.type=token_count` and `payload.info.total_token_usage` containing `input_tokens`, `output_tokens`, and `total_tokens`. Every recognized record's outer `timestamp` must be valid and session ID must match the candidate filename. Cache/reasoning counters may be parsed as non-negative safe integers but are not exposed; the three primary counters must be present together or all null. Unknown event types with valid JSON are ignored. Unknown keys and all strings outside the listed fields are discarded immediately. Do not return raw JSONL rows or keep message/content/error fields in result objects. Add synthetic fixtures for these event shapes and a changed-schema case.
- `GET /api/telemetry` returns exactly `{ "state": "ok"|"empty"|"ambiguous"|"unavailable", "session": null|{ "id": string, "updatedAt": string|null }, "usage": { "inputTokens": number|null, "outputTokens": number|null, "totalTokens": number|null }, "speed": { "outputTokensPerSecond": number|null, "state": "available"|"unavailable" } }`. No additional properties are permitted. Errors expose only a bounded error code/message and never filesystem paths or source lines.
- API code constructs a fresh response object from this allowlist; it never serializes parser objects. Tests use prompt, response, error, metadata text, and an oversized unknown field in fixtures and assert none occurs in the exact serialized response.
- Read only bounded tails of files matching the rollout filename pattern (maximum 2 MiB per file, 256 KiB per complete JSONL line, 8 MiB total per refresh). Skip a partial first line caused by the bounded-tail boundary and an unterminated final line caused by a concurrent append; parse no fields from either. Any malformed complete line, oversized complete line, invalid metadata, read error, or filename/event ID mismatch in an in-scope candidate makes the entire refresh `unavailable`; never log line contents or select from remaining files.

## Session selection and speed rules

- Candidate filename must match `rollout-<date-and-time>-<36-character-lowercase-UUID>.jsonl` (and the documented reverted-rollout suffix is rejected for the active-session scan); the final UUID is the conversation id and must match every recognized `session_meta.payload.id` in the bounded tail. It is not compared with `payload.session_id`, which is a separate Codex field. Consider matching files modified in the last 10 minutes, newest first. If more than 100 are in scope or reading all in-scope files would exceed the 8 MiB refresh budget, return `unavailable`; never make a partial choice. A candidate is active only if it has a valid recognized event within the last 10 minutes according to wall clock. Valid stale files and valid files with no recent recognized events are inactive and excluded. With no active candidate, return `empty` and null session/usage. With one candidate, select it. With multiple active candidates, select the greatest valid event timestamp; ties are broken by descending file modification time and then ascending session id. If the newest timestamps differ by at most one second and file mtimes by at most one second, treat as genuinely ambiguous and return `ambiguous` rather than imply an incorrect current conversation.
- Wall-clock values more than 5 minutes in the future are invalid. If system time moves backwards during one process lifetime, clear speed samples and report speed unavailable until two new monotonic samples exist.
- The server refresh worker polls telemetry every 1 second and owns all file reads; the browser polls `GET /api/telemetry` every 1 second and never starts a competing reader. Return `unavailable` if the worker's last refresh is more than 3 seconds old. Inject wall/monotonic clocks and the worker scheduler so tests advance time deterministically without sleeping. Keep only the last two distinct non-null usage samples in memory for the selected session. On successful `ok` refreshes, record a sample only when counters changed; the first sample is unavailable. A later sample calculates output tokens/s only when output increases and monotonic delta is 0.5-5 seconds. Identical polls do not replace a distinct sample; retain the most recent estimate for at most 5 seconds after its measurement, then show unavailable. An increase outside the interval becomes the new baseline without an estimate. Counter decrease, session change, null usage, non-ok refresh, stale source data (>10 seconds), wall-clock rollback, or process restart clears samples and the retained estimate. No sample persists to disk. Tests inject both clocks and the scheduler and assert unavailable after the first sample, 20 tokens/s from a 20-token increase over 1 second, retention across unchanged polls for up to 5 seconds, expiry afterward, and reset cases.
- Each refresh reads a bounded file snapshot using file identity, length, and last-write time before and after reading. If metadata changes, retry that candidate once. On a second change, mark the entire telemetry refresh `unavailable`; do not select among a partial candidate set or reuse prior results. No candidate cache survives a refresh. A deleted, truncated with malformed complete data, unreadable, or filename/event-ID-mismatched in-scope file makes the whole refresh `unavailable`; ignore a final unterminated line until a later poll. If file-count or byte limits prevent evaluating every in-scope candidate, return `unavailable` rather than infer `empty`, `ok`, or `ambiguous` from a partial scan. The parser recognizes only the event shapes and property paths above and discards all other properties before creating its internal snapshot. This avoids serving a last-known or incomplete scan as current.

## Benchmark process contract

- Resolve the native executable named `codex.exe` from PATH during server startup, canonicalize it, verify it is a file, and retain that exact path for process lifetime. Refuse startup of benchmark feature with a structured unavailable state if resolution fails. Never invoke PowerShell shims, `cmd.exe`, shell mode, a browser-supplied path, or a shell command string.
- For each fixed case, invoke the absolute resolved `codex.exe` with fixed argv equivalent to `exec --json --ephemeral --ignore-user-config --skip-git-repo-check --sandbox read-only --model <selected-model> -c model_reasoning_effort=<selected-effort> -`, and send the compiled case prompt via stdin. These supported flags were checked with the installed `codex exec --help`. Model and reasoning are selected from the exact fixed allowlists above and validated server-side; use a newly created empty temp cwd under the app's own temp directory. Do not pass through caller environment wholesale. Construct the child environment from exactly `SystemRoot`, `WINDIR`, `TEMP`, `TMP`, `PATH`, `USERPROFILE`, plus `CODEX_HOME` only when `%USERPROFILE%\.codex` exists. Values come from the server's startup environment and are validated as existing directories where applicable. `PATH` is pinned to the directory containing the resolved native `codex.exe`, the Node runtime directory, and `%SystemRoot%\System32`; `CODEX_HOME` is set to `%USERPROFILE%\.codex` solely so the CLI can use existing authentication. The companion never inspects, copies, logs, serializes, or exposes auth contents and never adds or alters credentials. `--ignore-user-config` prevents loading the user's Codex config; no profile, add-dir, image, output-file, or config-file argument is accepted. Do not pass any other variable, including proxy variables, API keys, tokens, credential helpers, CLI overrides, and config overrides. Tests assert the exact key set, values, flags, executable, cwd, stdin, and absence of credential/config variables.
- Fixed benchmark cases live in source and are versioned by `caseSetVersion`; browser requests cannot submit cases or prompts. Run one case at a time. Limit each run to 120 seconds, stdout to 1 MiB, stderr to 64 KiB. Continue draining pipes after the stored limit; mark output as truncated and fail the case if a complete JSONL final-answer event cannot be obtained. Do not show or persist raw stderr.
- On timeout or cancel, send termination to the process and its descendants using Windows process-tree termination (`%SystemRoot%\System32\taskkill.exe /PID <pid> /T /F` with fixed executable and validated numeric pid), wait up to 5 seconds, then report cleanup failure distinctly. Never use shell interpolation for taskkill; invoke it as a fixed executable with argv.
- Case states are `queued|running|completed|failed|timed_out|cancelled`; a run is `queued` before its first case, `running` while any case is active, and terminal only after every fixed case reaches a terminal case state. Parse JSONL one bounded line at a time; accept exactly one `item.completed` event with `item.type=agent_message` and bounded string `item.text`, followed by `turn.completed` with completed status and process exit code 0. Ignore other event types without storing their contents; reject malformed JSON, multiple final messages, missing final message/completion event, non-zero exit, or truncated output. Failures preserve a bounded diagnostic code only. Partial failed/cancelled runs cannot be scored as complete and cannot become baseline.
- Persist each run and request reservation with `{ requestId, requestPayloadHash, runId, status, createdAt, cliVersion, model, reasoningEffort, caseSetVersion, rubricVersion, schemaVersion, caseResults }`. The comparison key is exact equality of CLI major/minor, reasoning effort, case-set version, rubric version, and schema version; model is excluded from compatibility matching but remains a mandatory cohort key. The baseline pointer stores the selected runId and its compatibility key. An incompatible selection returns 409 and leaves baseline unchanged. Failed, interrupted, or cancelled runs never replace or mutate the current baseline.
- Save answer text and user scores locally because the benchmark requires side-by-side comparison; bound each answer to 16 KiB and reject control characters other than newline/tab. `GET /api/benchmark` returns only the newest 20 run summaries and the selected baseline anchor plus newest eligible comparison run with fixed case answers and scores; it never returns process output or raw diagnostics. Its exact response schema has a 256 KiB serialization cap. The UI displays answers only in the benchmark results view after the user starts a run. Telemetry responses never expose benchmark data. Scores are integers 1-5 per fixed rubric dimension; comparison reports per-dimension change and pre/post sample counts, with an explicit `inconclusive` label unless at least five compatible fully scored runs exist on each side. This describes observed scores for one model label and is not proof of degradation.
- Benchmark storage is under a dedicated app directory in `%LOCALAPPDATA%` with a 1000-run/64 MiB ceiling. Never delete history automatically; after the limit is reached, return a bounded unavailable state until the user removes the app data. Create files atomically. On Windows, set the directory ACL to the current user's SID only (full control, inherited by children) with fixed system `whoami.exe` and `icacls.exe` invocations; validate the SID and executable paths and fail benchmark storage closed if ACL setup fails. Persist request reservations before spawning; never store auth tokens, raw process environment, stdout beyond bounded final answers, or stderr. If the server exits during a run, terminate the process tree during orderly shutdown and mark any reservation with unknown outcome `interrupted` on next startup; never infer success or automatically repeat the child.

## Reproducible UI acceptance

- Start with `npm run dev`; expect the server to print `http://127.0.0.1:4173` only after binding succeeds. If the port is occupied, stop the other local server and rerun; the application does not change host or port. Stop with Ctrl+C after checks.
- Inspect at 1440x900 and 390x844. Pass if counters and labels fit without horizontal page scrolling, benchmark controls remain reachable, and no overlapping content appears.
- Normal state: use injected-clock fixture snapshots at t=0 and t=1s with input=120; output increasing from 60 to 80; and total increasing from 180 to 200. Continue two unchanged polls at t=2s and t=3s. Expect displayed counters 120 input, 80 output, 200 total and retained speed 20 output tokens/s at t=3s, with no wall-clock sleep.
- Empty state: point the test server to an empty temporary sessions directory. Expect “No active Codex session” and unavailable speed, without a stack trace.
- Error state: use a nonexistent sessions directory and separately send an invalid POST without nonce. Expect bounded “Telemetry unavailable” UI for the former and HTTP 403 with the fixed JSON error schema for the latter; no path/value is echoed. Also verify occupied-port startup fails without binding elsewhere.
- Loading state: delay the telemetry fixture response by 500 ms. Expect stable loading indicators and no stale values presented as current until the response resolves.
- Benchmark states: use a mocked runner to trigger queued/running/completed, non-zero failure, timeout, and cancel. Confirm only completed compatible runs can be selected as baseline and failures preserve the prior baseline. No real model run during development verification.
- Pass criteria: browser console has zero uncaught errors; all same-origin requests return expected status/schema; no request goes off loopback; the app stops and child processes are gone after verification.

## Rollback

All implementation files will be new. If abandoned, remove only project-created files and stop the local server. Do not change existing user configuration or hooks.

## Risks

- The Codex JSONL schema may change; unknown fields will be discarded, and no session should be represented as active if the known schema cannot be parsed.
- Timestamp granularity and concurrent sessions can make token/s unavailable or ambiguous.
- CLI JSON event formats may vary across versions; compatibility metadata and conservative failure states avoid false comparisons.
- Benchmark results vary with model, reasoning effort, and rubric; one run is not evidence of degradation.
- The companion UI requires final user acceptance after local visual verification.
