# Codex Stateline UI / 可用性审查

- 日期：2026-10-26
- 范围：Web 面板的真实渲染、320/375px 窄屏、深色/浅色 token、键盘与触控可达性、动态状态；原生窗口使用 fixture 复核尺寸与截图。
- 边界：只审查，不修复；未调用真实模型、未保存评分或基线、未执行业务 POST、未读取或复述个人任务标题。数据示例使用合成快照或只读脱敏统计。
- 结论：确认 **6 项 UI / 可用性问题（1 项同时属于主题适配缺口）**，编号在总报告中续接为 U-05～U-10。
- 说明：UI 审计员完成实测后由 lead 接管写盘；评分焦点项采用 lead 的独立串行复现。原始页面截图可能包含任务标题，不作为交付附件。

- Windows 10.0.26200.0；Node v26.1.0；浏览器 Chrome/155 渲染通道，现有 Edge 156 可用于后续人工复测。Web 地址为现有 `http://127.0.0.1:4173/`。
- 320×569、375×813 及桌面视口实测均无整页水平溢出。320px 下任务选择框 194.5px、跟随按钮 59.8px；没有据此声称全部长字符串均不会溢出。

- 深色 token 实测正文/辅助色 `#EDEEF2`、`#B0B3BF`、`#9A9EAC`，卡片底 `#1C1D21`，正文/辅助文本对比度约 5.72～8.06:1；未发现常规文本对比度不足。没有声称完成所有颜色组合的穷举。

- 原生现有自测与独立 fixture 显示结果窗重开、Esc、焦点恢复、错误时保留最后合法值等正常路径；不因测试通过推断所有实机场景无缺陷。

## U-05｜中｜同名任务使用相同短 ID，无法从选项中可靠区分

**证据：真实页面只读统计＋选择值验证＋源码。**

**复现**
1. 准备多个同名、且 UUID 前 8 位相同的不同任务。
2. 打开 Web 任务选择框，比较各 option 的可见标签。
3. 选择其中一项并查看完整值，区分“辨识困难”与“绑定错误”。

**实际**
- 审计时 50 项样本中有 8 组可见标签完全相同，组大小 `3/2/2/4/2/3/2/3`；每组完整 ID 不同。真实任务列表会变化，所以组数只是当时样本，不是固定数量。
- 标签来源为截到 44 字的标题加 8 位短 ID；同名且短 ID 冲突时视觉上完全一样。
- 选择值仍使用完整 UUID，实测能选中对应项，没有证明必然选错任务或串用数据。

**预期**：重复项应提供稳定消歧信息，例如序号、更新时间/来源上下文、可展开的完整标识或补充可访问名称。

**定位**：`src/public/app.js:61`、`src/public/app.js:70`、`src/public/app.js:89-95`；选择/固定在 `src/public/app.js:173-190`。

**影响**：用户必须猜测哪个条目是目标任务，固定和查看历史任务容易误选。原生 ComboBox 通过 tooltip 保留完整 ID，但 Web 没有等价的可见消歧。

**修复方向**：后端提供稳定显示标签或前端在重复组中追加可靠上下文/消歧序号；不要让完整 ID 仅存在于 tooltip。覆盖同名、短 ID 冲突、超长标题与键盘选择测试。

## U-06｜中｜代理完整详情只放在 title，窄屏、触控和键盘用户无法稳定取得

**证据：真实 DOM/尺寸＋源码。**

**复现**
1. 打开含代理信息的 Web 面板，将视口设为 320px。
2. 查看省略的代理行，用 Tab 和触屏尝试获取完整模型、推理强度、回合关联等详情。

**实际**
- 可见代理行宽约 262.4px；样本行 `scrollWidth` 达 265px、294px，CSS 强制单行省略。
- 行是普通 `<p>`，`tabIndex=-1`，没有按钮、展开详情或可聚焦元素；完整细节只在 `title` 中。
- 触控没有可靠 hover，键盘无法将焦点移到这些行。容器最大高 72px，样本可视约 71px、内容 72px，还有轻微裁行风险。

**预期**：提供可聚焦、可点击的详情展开，或允许信息换行/独立详情面板；完整信息不能只靠鼠标 tooltip。

**定位**：`src/public/app.js:72-87`，尤其 `82-85`；`src/public/styles.css:460-479`。

**影响**：用户不能可靠辨认日志模型、推理强度、状态及关联回合，既损失信息也影响辅助技术使用。

**修复方向**：每行使用语义化 button + 可展开区域，支持 Enter/Space、触控及可见焦点；或将字段改为可换行的定义列表。代理区可滚动时提供合理高度与可见滚动提示。

## U-07｜中｜结果刷新替换评分控件，焦点和屏幕阅读器上下文丢失

**证据：lead 使用合成只读快照在真实浏览器串行复现＋源码。**

**复现**
1. 让基准结果在评分完成后再次收到非 progress 的新快照，例如服务端模型默认值改变。
2. 在评分 select 中把未保存草稿改为 5 并聚焦该控件。
3. 等下一轮 1.5 秒快照，检查节点与焦点；本审计只拦截 GET，没有发送评分 POST。

**实际**
- 刷新前 `focused=true`、`value=5`；刷新后原 select 与新 select `sameNode=false`，`activeElement=BODY`。
- 草稿值因 `state.drafts` 保留为 5，但键盘焦点、控件身份和读屏上下文丢失。并非所有 progress 刷新都重建，问题是任何导致 render key 改变的有效快照。

**预期**：保留正在编辑的评分 DOM 和焦点；仅更新真正改变的字段。草稿保留不应以丢失操作位置为代价。

**定位**：`src/public/app.js:323-325`、`328-340`、`353-360`；`334` 清空并重建所有 cases，`360` 在 key 变化时整体渲染。

**影响**：键盘用户连选多个评分时会被打断，并可能误操作后续控件；连续选择草稿不一定丢失，但输入过程不可靠。

**修复方向**：按 run/case 做局部、可 keyed 的 DOM 更新；刷新前记录焦点与选择，只在必要时更新对应控件；增加“聚焦评分时收到新快照”的浏览器测试。

## U-08｜低｜推理强度与运行按钮在同一网格行顶对齐，底边错位约 20.5px

**证据：桌面与 375px 实测＋源码。**

**复现**：展开“鹈鹕基准”，比较“推理强度”控件和右侧“启动基准”按钮。

**实际**
- 桌面样本按钮与推理强度底边相差 20.47px；375px 复现差约 20.5px。
- 带标签的 label 高约 50.5px，独立按钮只有 30px；两者同属第二行网格，按钮从行顶开始，而不是与 select 对齐。

**预期**：同一行表单控件保持共同基线或底边；按钮应和 select 对齐，不应像贴在标签文字旁边。

**定位**：`src/public/index.html:14`；`src/public/styles.css:239-255`，尤其 `.controls` 的两列网格及 `label` 的内部 grid。

**影响**：操作分组和视觉对应关系不清晰，属于可测量的对齐问题，不是风格偏好。

**修复方向**：将按钮包装为与其他字段同构的 grid 项，保留标签空间；或按控件区域 `align-self:end`。验证窄屏和取消按钮状态。

## U-09｜低｜整个高频遥测面板被设为 live region，可能干扰真正重要的播报

**证据：真实 DOM 变更观察＋源码；读屏实际播报尚未实测。**

**复现**
1. 用辅助技术或 MutationObserver 观察 `.panel[aria-live=polite]`。
2. 保持页面正常运行约 2.2 秒，观察其子树更新。

**实际**
- 整个“对话消耗”面板设置 `aria-live="polite"`，任务计时、代理、指标、详情都在同一区域。
- 一次 2.2 秒观察记录 28 次 `childList` 更新；轮询每秒触发。DOM 变更次数不等于读屏必然播报 28 次，具体冗长程度依赖浏览器和辅助技术。

**预期**：只让简短连接状态、错误或关键任务状态进入 live region；计时与普通遥测更新默认不主动播报，并避免无实际文本变化的通知。

**定位**：`src/public/index.html:6`；`src/public/app.js:192-230`、`391`。

**影响**：可能反复打断读屏用户，使重要错误/连接信息淹没在常规刷新中。严重度低是因为实际播报量待 NVDA/JAWS 等环境复核。

**修复方向**：移除整个面板的 live 属性，给精简的 status/error 节点设置独立 live；仅文本实际改变时更新，并做读屏人工验收。

## U-10｜低｜浅色主题已有 token，但没有主题初始化或切换入口

**证据：真实 `prefers-color-scheme` 检查＋源码；属于适配缺口。**

**复现**：在系统/浏览器浅色偏好下打开 Web，检查根元素主题和计算后的 `color-scheme`。

**实际**
- `prefers-color-scheme: light` 为 true 时，`data-theme=null`、`color-scheme=dark`；没有手动切换入口。
- 浅色 token 已定义，注释要求 JS 根据系统偏好设置，但入口初始化没有实现。

**预期**：若产品支持浅色，应按偏好或用户选择设置 `data-theme`，并同步 `color-scheme`；若只支持深色，应明确支持范围、删除误导性实现注释。

**定位**：`src/public/tokens.css:100-147`，`166-172`；`src/public/index.html:3`；`src/public/app.js:391`。设计文档 `docs/ui-redesign/codex-stateline-ui-redesign.md:675-678` 把浅色切换写为“若要做”，因此不把它升级为违约的高严重度故障。

**影响**：已有代码承诺与产品行为不一致，浅色偏好的用户始终获得深色界面；不影响当前深色主题本身的使用。

**修复方向**：明确主题支持边界；实现时在首屏前设置主题，监听系统变化或提供持久化切换，并验证所有状态的对比度。
